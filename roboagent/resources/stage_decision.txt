DECISION UNIT: VERIFIED OPERATION STAGE
A model decision generates one coherent, multi-action operation stage with explicit entry checks, measurable progress checks, and an exit condition. This is a scheduling/execution protocol. No stored task solutions or previous episode trajectories are supplied.
Do not spend a model round merely printing perception when current evidence supports proceeding. Combine perception, geometry estimation, planning and bounded motion within the stage. Execute multiple small waypoints in one code block; do not request another model decision after every waypoint. Read fresh observations inside the block to check progress.
Typical manipulation boundaries: (1) localize and reach a verified pre-interaction pose; (2) establish and test the intended interaction, e.g. approach/close/short lift with visual evidence; (3) transfer and align while maintaining that interaction; (4) finish/release/retract and acquire final verification. These are examples, not mandatory task scripts. Choose boundaries from current evidence. Aim for 4–6 model decisions for a simple manipulation, including final verification; never stop or assert success just to meet a round target.
Before motion validate finite geometry, target selection, reachable IK and remaining per-block/episode budget. After each waypoint check actual robot pose/tracking error in code; continue when checks pass. A stage ends at its verified exit condition, unresolved ambiguity, failed check, API failure, or budget boundary. Catch recoverable API errors narrowly and at most twice; bound all correction loops, reacquire evidence after disturbances, and return to the model if recovery fails. No broad exception handler that silently continues manipulation.
Persist current-episode geometry and helper functions. Reuse static-object estimates while their evidence remains valid; refresh moved or occluded objects. Do not blindly reuse stale coordinates. Perception uncertainty affecting grasp or release warrants a model checkpoint; successful low-level checks do not. Verify object-following after a test lift before long transfer; verify alignment before release. Use only authorized RGB-D/self-state/API results, never hidden object states/contact/reward.
Use local_correction to state the stage plan and entry conditions; expected_visual_effect to state its verifiable exit condition. Print concise stage evidence (chosen target confidence, requested/actual pose error, observed object motion, remaining budget) rather than every waypoint state. On early return print the failed check and achieved substage so the next round resumes correctly. Keep the full audit history and existing budgets/physics/evaluation unchanged.
